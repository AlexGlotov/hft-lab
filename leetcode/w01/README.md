# w01 — LC1, LC217, LC242, LC49

## LC217 Contains Duplicate — сравнение трёх подходов

```cpp
// (1) сортировка на месте
bool containsDuplicate(vector<int>& nums) {
    std::sort(nums.begin(), nums.end());
    for (size_t i = 1; i < nums.size(); ++i)
        if (nums[i] == nums[i - 1]) return true;
    return false;
}

// (2) unordered_set (хеш-таблица, не дерево — деревом было бы std::set)
bool containsDuplicate(vector<int>& nums) {
    std::unordered_set<int> seen;
    seen.reserve(nums.size());
    for (int x : nums)
        if (!seen.insert(x).second) return true;
    return false;
}

// (3) сортированная копия
bool containsDuplicate(const vector<int>& nums) {
    std::vector<int> copy = nums;
    std::sort(copy.begin(), copy.end());
    for (size_t i = 1; i < copy.size(); ++i)
        if (copy[i] == copy[i - 1]) return true;
    return false;
}
```

| | Время | Доп. память | Мутирует вход | Аллокаций |
|---|---|---|---|---|
| (1) In-place sort | O(n log n) | O(1) (у introsort — O(log n) на стек, без кучи) | да | 0 |
| (2) `unordered_set` | O(n) сред., O(n²) при коллизиях хеша | O(n) | нет | до n (узлы) + рехэши бакетов |
| (3) Sorted copy | O(n log n) | O(n) | нет | 1 |

**`unordered_set` — хеш-таблица, не дерево.** Деревом (красно-чёрным) был бы `std::set`: узлы 40+ байт, три указателя, промах кэша на каждом уровне обхода, зато упорядоченность и стабильные итераторы. `unordered_set` — бакеты плюс цепочки, амортизированная O(1), но рехэширование и та же погоня за указателями по цепочкам.

**Два разных явления, которые нельзя путать.** Коллизии хеша — разные ключи попадают в один бакет, цепочка вырождается в список, поиск деградирует до O(n), полный проход — до O(n²). Это меняет асимптотику. Конфликтные промахи кэша (cache conflict misses) — адреса отображаются в один и тот же set кэша при ограниченной ассоциативности; стоит тактов, но асимптотику не меняет вообще — кэш влияет на константу, не на сложность.

**Память: одна аллокация лучше n.** `unordered_set` выделяет узлы по запросу (до n вызовов `operator new`, каждый — сотни тактов) и разбрасывает их по куче (~32 байта на элемент: значение + `next` + накладные аллокатора), обход — погоня за указателями. Sorted copy делает одну аллокацию под непрерывный блок (4 байта на `int`), обход — последовательный, префетчер работает. При n порядка тысяч сортировка копии часто выигрывает у `unordered_set` по реальному времени, несмотря на худшую асимптотику — за счёт одной аллокации и последовательного доступа вместо n мелких и разбросанных.

## LC242 Valid Anagram — сравнение двух подходов

`valid_anagram_count.cpp` (счётчик по алфавиту) vs `valid_anagram_sort.cpp` (сортировка обеих строк).

| | Время | Доп. память | Аллокаций |
|---|---|---|---|
| Count (`vector<int> abc(26)`) | O(n) | O(1) (размер фиксирован алфавитом, не зависит от n) | 1 — `vector<int>(26)` всегда уходит в кучу |
| Sort (`sort(s)`, `sort(t)`) | O(n log n) | O(1) (сортировка на месте, у introsort O(log n) на стек) | 0 |

Асимптотически count строго лучше (O(n) < O(n log n)), но реализация счётчика платит за это одной кучевой аллокацией на каждый вызов (`std::vector<int>(26)` — это `operator new` на 104 байта), а сортировка — ни одной: `s` и `t` уже свои копии (параметры по значению), `sort` просто переставляет байты на месте. Ровно как в LC217: **на очень коротких строках** (типичные слова для этой задачи — единицы символов) фиксированная цена одной аллокации может перевесить разницу между `O(n)` и `O(n log n)`, и сортировка выигрывает по реальному времени. Если заменить `vector<int> abc(26)` на `std::array<int, 26>` или обычный `int abc[26]` (без кучи вообще), этот кроссовер исчезает — count побеждает практически всегда, не только асимптотически.

## LC49 Group Anagrams — цена хеширования сигнатурного ключа

`group_anagrams_sorted_key.cpp` (ключ — отсортированное слово) vs `group_anagrams_signature_key.cpp` (ключ — `string(26,'0')`, счётчик букв).

**Построение ключа.** У отсортированного ключа длина = длине слова `k`, построение — `O(k log k)` (сортировка). У сигнатурного ключа длина всегда ровно 26 байт независимо от `k`, построение — `O(k)` (один проход, без сортировки). Уже здесь сигнатура асимптотически лучше — убирает множитель `log k`.

**Хеширование ключа.** `unordered_map<string, ...>` хеширует и сравнивает ключ побайтово. Отсортированный ключ — `O(k)` на хеш, пропорционально длине слова. Сигнатурный ключ — **всегда ровно `O(26)`**, независимо от `k`. Для длинных слов (`k > 26`) это чистый выигрыш — хешируешь константное число байт вместо всего слова. Для типичных коротких слов LeetCode-теста (`k` — единицы символов, `26`-байтный ключ почти всегда длиннее самого слова) — это переплата: хешируешь фиксированные 26 байт ради представления 3–5-буквенного слова.

**Аллокация ключа — здесь основная цена.** У этой `libstdc++` SSO-буфер `std::string` — ровно 15 байт (проверено эмпирически: `capacity()` пустой и 15-байтной строки — 15, у 16-байтной уже 16 и куча). Отсортированный ключ для типичного английского слова (≤15 букв) **остаётся в SSO — без кучи**. Сигнатурный ключ — это `string(26, '0')`, **26 > 15 всегда**, поэтому он гарантированно уходит в кучу на **каждом** слове, сколько бы букв в этом слове ни было. Итог: сигнатурный подход асимптотически чище (никакой сортировки, фиксированная стоимость хеша), но на реалистичном для этой задачи входе (короткие слова) платит гарантированной аллокацией там, где отсортированный ключ почти всегда обходится без кучи вообще — тот же паттерн, что и в LC217/LC242: меньшая асимптотика не бесплатна, если реализация ключа платит за неё аллокацией на каждый элемент.
