## TMin

### 1. Диапазоны TMin/TMax для 32 и 64 бит — из B2T

Формула two's complement для w бит:
`value = -x_{w-1}·2^{w-1} + Σ_{i=0}^{w-2} x_i·2^i`.

TMin — знаковый бит 1, всё остальное 0: `value = -2^{w-1} + 0 = -2^{w-1}`.
TMax — знаковый бит 0, всё остальное 1: `value = 0 + Σ_{i=0}^{w-2} 2^i = 2^{w-1} - 1`.

| w | TMin | TMax |
|---|---|---|
| 32 | `-2^31 = -2147483648` | `2^31 - 1 = 2147483647` |
| 64 | `-2^63 = -9223372036854775808` | `2^63 - 1 = 9223372036854775807` |

Проверено `tmin.cpp` через `INT_MIN`/`INT_MAX` из `<climits>` — совпадает.

### 2. Почему |TMin| = |TMax| + 1

У w бит `2^w` паттернов, половина (`2^{w-1}`) уходит под неотрицательные
(`0 … TMax`), половина — под отрицательные (`TMin … -1`); но ноль сидит
в неотрицательной половине, поэтому отрицательных значений ровно
`2^{w-1}`, а неотрицательных (включая ноль) тоже `2^{w-1}`, но
положительных среди них — `2^{w-1} - 1` (ноль его не считать). Отсюда
`|TMin| = 2^{w-1} = (2^{w-1} - 1) + 1 = |TMax| + 1`.

### 3. `-TMin` в 32 битах

`INT_MIN` в исходнике намеренно проведён через `argc` (`int tmin =
INT_MIN + (argc - 1);`) — иначе GCC сворачивает `-INT_MIN` в константу
уже на этапе компиляции и сам ловит переполнение через `-Woverflow`,
и файл перестаёт собираться чисто под `-Wall -Wextra`. Тот же приём,
что уже использован в `experiments/w00_sanity/heap_overflow.cpp`.
UBSan при этом видит ровно то же самое переполнение — только в рантайме,
не статически:

```
$ g++-14 -std=c++20 -Wall -Wextra -fsanitize=undefined -g -o tmin_ubsan tmin.cpp
$ ./tmin_ubsan
tmin.cpp:12:16: runtime error: negation of -2147483648 cannot be represented in type 'int'; cast to an unsigned type to negate this value to itself
INT_MIN            = -2147483648
INT_MAX             = 2147483647
-INT_MIN            = -2147483648
(unsigned)INT_MIN   = 2147483648
```

С `-fno-sanitize-recover=undefined` (строгий режим) программа падает
сразу на этой строке, до печати остального вывода:

```
$ g++-14 ... -fsanitize=undefined -fno-sanitize-recover=undefined ...
tmin.cpp:12:16: runtime error: negation of -2147483648 cannot be represented in type 'int'; cast to an unsigned type to negate this value to itself
$ echo $?
1
```

Это **UB для знакового типа** — `+2^31` не представимо в `int`
(диапазон до `2^31-1`), и стандарт здесь не гарантирует вообще ничего,
включая «получится то же число». То, что на практике `-INT_MIN`
печатает тот же битовый паттерн `INT_MIN` (аппаратное two's-complement
отрицание — инвертировать биты и прибавить 1 — для `1000...0` циклически
возвращает `1000...0`) — это следствие конкретной реализации
(железо + отсутствие ловушек на переполнение), а не то, что обязан
делать компилятор. UBSan сам явно фиксирует UB, а не «всё в порядке,
просто совпало число».

## LC 268 — переполнение суммы Гаусса

### При каком n формула `n*(n+1)/2` переполняет 32-битный int

**n = 46341.** `46341 * 46342 = 2147534622 > INT_MAX (2147483647)` —
переполняется само произведение `n*(n+1)`, ещё до деления на 2, хотя
итоговое значение `n*(n+1)/2 = 1073767311` спокойно помещается в `int`
(меньше половины `INT_MAX`). При n=46340 всё ещё умещается:
`46340*46341 = 2147441940 < INT_MAX`.

Доказано запуском `missing_number.cpp` на массиве размера ровно 46341:
```
missing_number.cpp:7:22: runtime error: signed integer overflow: 46341 * 46342 cannot be represented in type 'int'
n = 46341 (naive n*(n+1) = 2147534622, overflows 32-bit int)
gauss naive = -2147437307
gauss safe  = 46341
xor         = 46341
sort        = 46341
expected missing = 46341
```
`gauss naive` возвращает мусор (`-2147437307` вместо `46341`) — не
«почти правильно», а произвольное значение, дальше на него полагаться
нельзя.

### Как это чинится без перехода на 64 бита

Не «взять `long long`» — поменять порядок операций так, чтобы
промежуточный результат не был искусственно раздут вдвое перед
делением:

```cpp
int expected = (n % 2 == 0) ? (n / 2) * (n + 1) : n * ((n + 1) / 2);
```

Один из множителей делится на 2 **до** умножения (гарантированно без
остатка — один из `n`/`n+1` всегда чётный), поэтому промежуточное
значение примерно равно самому финальному ответу, а не вдвое больше
него. Порог переполнения при этом сдвигается ровно туда, где начинает
переполняться уже сам математический результат — `n = 65536`
(`(65536/2)*65537 = 2147516416 > INT_MAX`), при n=65535 ещё умещается
(`2147450880`). До этой границы `missingNumberGaussSafe` корректен —
проверено (`gauss safe = 46341`, совпадает с ожидаемым).

### Почему у XOR-решения этой проблемы нет вообще

```cpp
int result = n;
for (int i = 0; i < n; ++i) result ^= i ^ nums[i];
```

XOR — побитовая операция без переноса между разрядами. Результат
`a ^ b` для любых 32-битных `a`, `b` — всегда корректное 32-битное
значение, «переполнить» его нечем: нет понятия величины, которая могла
бы вырасти за пределы диапазона, есть только независимые биты. У сложения
и умножения есть перенос (величина растёт и может не поместиться), у
XOR — нет и в принципе не может быть.

## LC 191 — трюк Кернигана

### Почему `n &= n - 1` гасит ровно один младший установленный бит

Пример: `n = 0b10110000` (176).

```
  n      = 1011 0000
  n - 1  = 1010 1111   (заём распространяется через хвостовые нули,
                         они становятся единицами, младший установленный
                         бит гасится)
  n & (n-1) = 1010 0000
```

`n-1` переворачивает все хвостовые нули в единицы и обнуляет младший
установленный бит; всё выше него не трогает. При `AND` с исходным `n`:
на позиции младшего установленного бита — `1 & 0 = 0` (погашен), на
хвостовых нулевых позициях — `0 & 1 = 0` (и так были нулём, не
изменилось), везде выше — биты совпадают и остаются как были. Итог:
ровно один бит погашен, остальные нетронуты.

### Число итераций: наивный сдвиг vs Кернигана

Проверено `number_of_1_bits.cpp`:
```
n = 0x00000001: naive=1 (1 iter), kernighan=1 (1 iter), std::popcount=1
n = 0x80000000: naive=1 (32 iter), kernighan=1 (1 iter), std::popcount=1
n = 0x000000B0: naive=3 (8 iter), kernighan=3 (3 iter), std::popcount=3
```

| n | наивный сдвиг | Керниган |
|---|---|---|
| `1` (`0b1`) | **1** | **1** |
| `0x80000000` (`0b1000...0`, бит 31) | **32** | **1** |

Наивная версия крутится, пока `n` не станет 0, — число итераций равно
позиции старшего установленного бита + 1, **не зависит от того, сколько
битов реально установлено**. У `0x80000000` единственный установленный
бит, но он старший — наивный вариант всё равно проходит все 32 позиции.
Керниган на каждой итерации гасит ровно один установленный бит — число
итераций равно popcount, и для `0x80000000` это 1, независимо от того,
что бит лежит в самом старшем разряде.

### `std::popcount` на `-O2 -march=native`

Godbolt: https://godbolt.org/z/8dEY4Y6K9

```cpp
int popcount32(uint32_t n) { return std::popcount(n); }
```
компилируется в одну инструкцию:
```asm
popcount32(unsigned int):
  popcnt eax, edi
  ret
```
Никакого цикла — `std::popcount` при поддержке целевой архитектурой
(`-march=native` на хосте Godbolt) превращается напрямую в аппаратную
инструкцию `popcnt`, O(1) вместо ручного цикла любой из двух версий
выше.

## Контрольный вопрос

`cmp(-1, 1u)` — оба операнда участвуют в usual arithmetic conversions:
`unsigned int` имеет тот же ранг, что `int`, поэтому по правилам
стандарта знаковый операнд конвертируется в беззнаковый, а не наоборот
— `-1` как `unsigned int` превращается в `UINT_MAX = 4294967295`, и
сравнение `4294967295 < 1` закономерно ложно (`cmpUnsignedInt(-1, 1u)`
у нас реально печатает `0`); ровно тот же механизм и с `unsigned long`
(ранг выше `int`, конвертация всё равно в беззнаковый, только `-1`
превращается в `ULONG_MAX` на 64-битном `long` — `cmpUnsignedLong`
тоже даёт `0`, и `-Wsign-compare` предупреждает про оба случая, а под
`-Werror` оба обязаны провалить сборку). С `unsigned short` картина
другая: его диапазон (16 бит) целиком помещается в `int` (32 бита),
поэтому по правилу integer promotion `unsigned short` сначала
повышается до **`int`**, а не до `unsigned` — сравнение реально
происходит между двумя `int`, знаковая семантика не нарушается, `-1 < 1`
честно истинно (`cmpUnsignedShort` печатает `1`), и компилятор здесь
`-Wsign-compare` даже не выдаёт — предупреждать не о чем, потому что
никакой опасной конверсии в беззнаковый тип фактически не произошло.
