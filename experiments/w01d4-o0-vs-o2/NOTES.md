# W01 D4 — -O0 vs -O2: куда девается работа

Все прогоны — Godbolt, `x86-64 gcc 14.2` (`g142`), `-std=c++20`. Локально
перепроверено на `g++-14` 14.2.0 из этого репозитория — структура и число
инструкций совпадают полностью. Единственное расхождение — на `-O0`
порядок стековых слотов `s`/`i` зеркально отличается от Godbolt (`rbp-4`
↔ `rbp-8` меняются местами): у Ubuntu-пакета `g++-14` по умолчанию включены
`-fstack-protector-strong`/`-fPIE` (проверено `g++-14 -Q --help=common`),
у ванильной сборки на Godbolt — нет, это чуть меняет раскладку кадра, но
не число и не состав инструкций.

## 1. Трафик к стеку: `sum(const int*, int)`, `-O0` vs `-O2`

Источник: `sum.cpp` · Godbolt (обе конфигурации в одной ссылке):
https://godbolt.org/z/s5sdvc48j

### `-O0`

```asm
.L3:
  mov eax, DWORD PTR [rbp-8]     ; load i
  cdqe
  lea rdx, [0+rax*4]
  mov rax, QWORD PTR [rbp-24]    ; load a
  add rax, rdx
  mov eax, DWORD PTR [rax]       ; load a[i]        <- единственное обращение не к своему кадру
  add DWORD PTR [rbp-4], eax     ; s += eax: read-modify-write s
  add DWORD PTR [rbp-8], 1       ; i++: read-modify-write i
.L2:
  mov eax, DWORD PTR [rbp-8]     ; load i
  cmp eax, DWORD PTR [rbp-28]    ; load n, compare
  jl .L3
```

Каждая локальная переменная (`a`, `n`, `s`, `i`) живёт в своём слоте
стека и перечитывается/переписывается заново на каждой итерации — компилятор
не держит вообще ничего в регистрах между операциями, только использует
их как временные внутри одной инструкции.

Обращений к памяти на итерацию (тело `.L3` + проверка условия `.L2`,
оба блока выполняются по разу за итерацию):
- `.L3`: load i, load a, load a[i], (read+write) s, (read+write) i → 1+1+1+2+2 = **7**
- `.L2`: load i, load n → **2**
- **Итого 8 обращений к своему стек-кадру + 1 обращение к реальным данным (`a[i]`) = 9 обращений к памяти на итерацию.**

Что лежит в этих 8 «стековых» обращениях — не данные задачи, а сам факт,
что `-O0` честно материализует каждую переменную исходника в память между
операциями: `a` (указатель, 8 байт), `n`, `s`, `i` (по 4 байта). Только
одно обращение из девяти — `a[i]` — действительно про данные.

Инструкций в теле цикла: 8 (`.L3`) + 3 (`.L2`: mov, cmp, jl) = **11 на
итерацию**, если считать и проверку условия; если считать только «тело»
в узком смысле (`.L3`) — **8**.

### `-O2`

```asm
.L3:
  add eax, DWORD PTR [rdi]   ; s += *ptr, накопитель прямо в регистре
  add rdi, 4                 ; ptr++ (регистр, не память)
  cmp rdi, rdx                ; сравнение с precomputed end-указателем (регистр, не память)
  jne .L3
```

`s` живёт в регистре `eax` от начала и до `ret` — ни разу не выгружается
в память, `eax` — это заодно и регистр возврата, лишней работы вообще
нет. `i` исчез целиком: компилятор превратил индексацию `a[i]`/`i < n`
в сравнение указателей — `rdi` бежит по массиву напрямую, `rdx` заранее
посчитан как `a + n*4` (конец диапазона), инкремент — `add rdi, 4`. Это
классическая strength reduction/устранение индукционной переменной: цикл
по индексу превращён в цикл по указателю.

Обращений к памяти на итерацию: **1** (`[rdi]` — сами данные массива,
больше ничего).
Инструкций в теле цикла (`.L3`): **4** (`add`, `add`, `cmp`, `jne`).

Стекового кадра нет вообще — ни `push rbp`, ни единого обращения к
`[rbp±N]`. Дополнительно: GCC не автовекторизует этот цикл на `-O2` —
дерево-векторизация (`-ftree-vectorize`) включается только с `-O3`,
здесь честный скалярный цикл.

| | Обращений к памяти/итерацию | из них к стеку | Инструкций в теле |
|---|---|---|---|
| `-O0` | 9 | 8 | 8 (11 с проверкой условия) |
| `-O2` | 1 | 0 | 4 |

## 2. Инлайнинг: `call_sum(a)` = `sum(a, 8)`, `-O2` vs `-O2 -fno-inline`

Источник: `call_sum.cpp` · Godbolt: https://godbolt.org/z/h1sn17PhW

### `-O2` (инлайнинг включён по умолчанию)

```asm
call_sum(int const*):
  movdqu xmm1, XMMWORD PTR [rdi+16]
  movdqu xmm0, XMMWORD PTR [rdi]
  paddd xmm0, xmm1
  movdqa xmm1, xmm0
  psrldq xmm1, 8
  paddd xmm0, xmm1
  movdqa xmm1, xmm0
  psrldq xmm1, 4
  paddd xmm0, xmm1
  movd eax, xmm0
  ret
```

`call` не осталось вообще — ни к `sum`, ни к чему-либо ещё. При этом
цикла тоже не осталось: при известной границе (`n = 8`, немаленькое, но
достаточно малое число) GCC полностью развернул цикл (complete unroll)
и затем упаковал получившуюся прямую арифметику в SIMD (SLP-vectorize,
она включена уже на `-O2`, в отличие от полной автовекторизации циклов
— увидели инструкции `movdqu`/`paddd`/`psrldq`, попарное дерево сложения
восьми `int` через XMM-регистры). Это возможно только потому, что `n=8`
стало известно компилятору *после* инлайнинга — `sum` сама по себе,
скомпилированная отдельно, не знает, что её будут звать с константой.

### `-O2 -fno-inline` (тот же проход векторизации, но без подстановки тела)

```asm
call_sum(int const*):
  mov esi, 8
  jmp sum(int const*, int)
```

Инлайнинга нет — `sum` осталась отдельной функцией с ровно тем же телом,
что в эксперименте 1 (обычный скалярный цикл, `n` — рантайм-параметр,
про восьмёрку ничего не знает). Но и здесь **`call` тоже пропал** — это
не инлайнинг, а отдельный, более узкий проход: сибл-колл-оптимизация
(sibling call / tail call), она применима, потому что вызов `sum` —
последняя операция перед `return`, и GCC заменяет `call+ret` парой
`mov+jmp`. Легко спутать «нет call» с «заинлайнилось» — это разные
механизмы, и без `-fno-inline` их эффекты неразличимы в выводе.
Инлайнинг именно физически подставляет тело и тем самым открывает
константе `n=8` доступ внутрь цикла для дальнейшей оптимизации (unroll +
vectorize); tail-call-оптимизация экономит только сам переход, тело
чужой функции остаётся непрозрачным.

## 3. Мёртвый код: `bench()`, `-O2`

Источник: `bench.cpp` · Godbolt (`-O0` и `-O2` рядом):
https://godbolt.org/z/YG8oj5r63

```asm
bench():
  ret
```

От функции не осталось ничего, кроме `ret` (на `-O0` тот же миллион
итераций — честный цикл с ровно той же структурой обращений к памяти,
что в эксперименте 1, `-O0`-версии `sum`, — можно свериться по ссылке).

Компилятор имел на это полное право по as-if rule: `s` — локальная
автоматическая переменная, в неё только пишут (`s += i * i`), из неё
никогда не читают — ни `return`, ни глобальный/статический эффект, ни
вывод, ничего. Наблюдаемое поведение программы (что она печатает, что
пишет в память, которую видит кто-то ещё, какие у неё побочные эффекты)
определяется только тем, что происходит с объектами, время жизни
которых выходит за пределы функции, или с side-effect-операциями
(I/O, volatile, atomics). Здесь таких нет вообще: `s` и `i` умирают
вместе со стековым кадром, весь цикл — вычисление, результат которого
никто никогда не наблюдает. Убрать его целиком — не искажение
программы, а единственно возможное поведение, неотличимое от
исходного с точки зрения любого внешнего наблюдателя. (Отдельно:
`i * i` для `i` близких к 1000000 переполняет `int` — это UB, и
компилятор вправе был бы удалить цикл и по этой причине тоже, но
основная и достаточная причина — dead store elimination, UB здесь
для итога не обязателен.)

Именно из-за этого наивный `for` в микробенчмарке без чтения
результата — не бенчмарк, а измерение времени пустой функции; вернёмся
к этому предметно на W19.
